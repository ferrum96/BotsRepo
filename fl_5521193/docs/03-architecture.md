# 3. Архитектура

## Схема

```
                    ┌──────────────────────────────┐
                    │  React Admin (Vite + Refine) │

  webhooks amoCRM ────────►│  валидация, RBAC  │        │  источник истины:  │
  webhooks магазина ──────►│  постановка задач │        │  данные + очередь  │
```

## Принципы

**amoCRM — рабочий интерфейс менеджера, а не источник истины.** Менеджеры живут в amoCRM: там карточка, там переписка, там задачи. Но состояние автоматизации, реестр идентификаторов, аудит и события живут в PostgreSQL, потому что amoCRM не даёт ни транзакций, ни нормализованного поиска, ни нужных гарантий уникальности.

**PostgreSQL — единственное состояние системы.** Данные, очередь задач и журнал событий в одной базе. Один бэкап, одна точка восстановления, одна транзакционная граница. Постановка задачи и бизнес-запись коммитятся вместе — это устраняет целый класс расхождений между БД и очередью.

**Ни один модуль не ходит в amoCRM напрямую.** Только через `AmoApiClient` с общим лимитером, и только из воркера.

**Проверки разрешения на отправку — в самом низком слое.** Suppression-list, статус автоматизации, лимиты, окно отправки проверяются внутри `send()`, а не в вызывающем коде. Забыть проверку невозможно, потому что её нельзя обойти.

**Одна джоба — один шаг.** Никаких длинных сценариев со сном. Каждый шаг заново читает актуальное состояние.

## Деплой-юниты

Один репозиторий (pnpm workspace), три образа: `api`, `worker`, `web`. `api` и `worker` — один и тот же код с разной точкой входа: API не выполняет джобы, воркер не слушает HTTP кроме `/health`. Это позволяет масштабировать и перезапускать их независимо, а падение воркера не роняет админку.

```
apps/
  api/            NestJS HTTP: REST, вебхуки, RBAC, OpenAPI
  worker/         NestJS standalone: обработчики очередей и cron
  web/            React + Vite + Refine
packages/
  contracts/      Zod-схемы и типы, общие для api и web
  db/             Drizzle schema + миграции
```

## Модули backend

```
core/
  amocrm/           throttled-клиент, OAuth, мапинг полей и статусов
  normalization/    чистые функции нормализации (100% unit-тестов)
  identity/         реестр идентификаторов, дедупликация, advisory locks
  messaging/        MessagingProvider, guard-цепочка, шаблоны
  outbox/           постановка задач в транзакции
modules/
  imports/          загрузка файла, парсинг, батчи, строки, retry
  contacts/
  deals/
  managers/         round-robin, лимиты, назначение
  automation/       стейт-машина, планировщик касаний
  qualification/    форма + scoring (конфиг версионируемый)
  onboarding/       воронка активации
  attribution/      промокоды, рефералы, продажи
  webhooks/         amocrm, магазин; проверка подписи, идемпотентность
  analytics/        события, вьюхи, агрегаты
  audit/            журнал действий, маскирование ПД
```

## Ключевые потоки

### Импорт

```
POST /imports (файл)
  → создать import_batch, сохранить файл, вернуть 202 и id
  → джоба parse: потоковое чтение, валидация схемы строки,
                 нормализация, дедуп внутри файла по идемпотентному ключу,
                 запись import_rows
  → джоба process-row на каждую строку (батчами):
        advisory lock по ключевому идентификатору
        поиск по реестру: телефон → tg id → email → username/url
        нет совпадения    → создать контакт + сделку
        есть совпадение   → дополнить пустые поля, добавить источник,
                            активная сделка есть → ничего не создавать
                            активной нет         → создать только сделку
        нечёткое совпадение → в duplicate_reviews, ждать человека
        записать решение в audit
  → джоба amocrm-sync: батчи по 50 сущностей через throttled-клиент
  → прогресс батча обновляется по ходу, импорт возобновляем
```

Ошибочная строка не останавливает импорт: у строки свой статус, своя причина ошибки и свой номер. `POST /imports/:id/retry-failed` перезапускает только упавшие.

### Первое касание

```
сделка создана
  → назначить менеджера (round-robin под блокировкой счётчика)
  → проверить, есть ли доступный автоканал
        нет → MANUAL_OUTREACH_REQUIRED, задача менеджеру, стоп
  → запланировать SEND_FIRST_MESSAGE на ближайшее окно отправки
  → воркер: FOR UPDATE по сделке, перечитать automation_status,
            guard-цепочка (suppression, лимиты, окно, канал),
            лимит исчерпан → перенос на следующее окно (не ошибка)
            рендер шаблона, сохранить фактический текст,
            отправка через amoCRM chats, записать message
  → запланировать followup D+3
```

### Входящий ответ

```
webhook (подпись, external_event_id для идемпотентности)
  → найти контакт по идентификатору чата
  → одной транзакцией:
        сохранить inbound message
        automation_status = STOPPED_BY_REPLY
        deal.stage = REPLIED
        задача менеджеру + уведомление
        событие REPLY_RECEIVED
  → best-effort отмена запланированных джоб
```

### Назначение менеджера

```
1. активные менеджеры, у которых есть нужный канал
2. отбросить исчерпавших дневной лимит
3. отбросить в отпуске / неактивных
4. round-robin по счётчику назначений
5. INSERT назначения и инкремент счётчика в одной транзакции
   (счётчик под FOR UPDATE — иначе два воркера дадут одному менеджеру двойную порцию)
6. передать responsible_user_id в amoCRM
7. если подходящих нет — сделка в очередь ожидания, событие в лог
```
