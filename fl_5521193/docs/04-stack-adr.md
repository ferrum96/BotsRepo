## ADR-001. Модульный монолит

**Оставляю.** Микросервисы здесь дали бы распределённые транзакции ровно там, где нужна атомарность (дедуп, назначение менеджера, остановка автоматизации), и утроили бы стоимость эксплуатации при команде из одного-двух разработчиков. Границы модулей соблюдаем в коде, чтобы вынести messaging или analytics позже, если появится причина.

## ADR-002. NestJS на Fastify-адаптере

**Оставляю.** Аргумент не в производительности, а в том, что NestJS даёт готовые ответы на задачи этого проекта: guards под RBAC, interceptors под correlation_id и аудит, DI под подмену внешних клиентов в тестах, декларативную генерацию OpenAPI для типизированного клиента фронтенда. Плюс это мейнстрим — проект можно передать другому разработчику.

Fastify вместо Express — как адаптер, разница в одну строку конфигурации, но заметно меньше накладных расходов на JSON и валидацию.

Что учитываю: NestJS не любят за многословность. Держим тонкие контроллеры и всю логику в сервисах, чтобы многословность не размножалась.

## ADR-003. Drizzle вместо Prisma

**Заменяю.** Prisma быстрее на старте, и на типовом CRUD я бы её и оставил. Но здесь критичные механизмы — это ровно те места, где Prisma не помогает:

| Что нужно | Prisma | Drizzle |
| --- | --- | --- |
| `pg_advisory_xact_lock` для дедупа | `$executeRaw`, без типов | `sql` с типизированными параметрами |
| Partial unique index («одна активная сделка на контакт») | Не выражается в схеме, только ручной SQL в миграции | Выражается в схеме декларативно |
| Функциональные индексы по нормализованным значениям | То же | То же |
| `INSERT ... ON CONFLICT DO UPDATE` с нужной семантикой | Ограниченный `upsert` | Полный контроль |
| `FOR UPDATE SKIP LOCKED` | Нет | Есть |
| Materialized views для аналитики | Вне модели | `sql` + миграции |

То есть при Prisma половина самой ответственной логики оказалась бы в нетипизированных строках SQL — при этом мы бы всё равно тащили Prisma-движок в образ и терпели её миграции. Drizzle — тонкий типизированный слой над SQL, схема и миграции в TypeScript, никакого отдельного бинарника.

Честный минус: экосистема Prisma больше, а Prisma Studio удобнее. Если у заказчика уже есть команда на Prisma — это приемлемая альтернатива, критичные места просто уходят в `$executeRaw` с ручными тестами. Но по умолчанию я выбираю Drizzle.

## ADR-004. pg-boss вместо Redis + BullMQ

**Убираю Redis и BullMQ из MVP.** Это самая существенная правка стека, поэтому обосную подробно.

**Главная причина — транзакционность, а не экономия.** С BullMQ создание сделки и постановка джобы на первое сообщение — две разные системы. Между `COMMIT` в PostgreSQL и `add()` в Redis есть окно: упали в нём — сделка есть, касания не будет, и это не видно ни в одном логе. Лечится это transactional outbox, то есть таблицей в PostgreSQL, отдельным диспетчером и дополнительными тестами. С pg-boss джоба — это строка в той же базе и в той же транзакции: либо есть и сделка, и задача, либо нет ни того, ни другого. Для системы, где потерянное касание означает потерянного партнёра, это принципиально.

**Вторая причина — нагрузка.** Считаем по ТЗ: 10–30 контактов в день на канал, база в десятки тысяч контактов, серия из пяти касаний. Это единицы задач в минуту в пике и порядка сотен в день. pg-boss на скромной машине держит тысячи задач в секунду. Запас более чем стократный. Причём сверху всё равно стоит потолок в 7 запросов в секунду к amoCRM — очередь физически не может стать узким местом.

**Третья причина — эксплуатация.** Минус контейнер, минус бэкап, минус мониторинг, минус класс инцидентов «Redis не сохранил / переполнил maxmemory / потерял джобы после рестарта».

**Что pg-boss даёт из нужного нам:** retry с exponential backoff, отложенный запуск (`startAfter`), cron-расписания, приоритеты, дедупликация через singleton-ключи (закрывает идемпотентность касаний), дохлые задачи в архиве вместо отдельной DLQ, конкурентность на очередь.

**Что теряем:** Bull Board — готовый UI очередей. Но по ТЗ (пункты «Очередь сообщений», «Логи интеграции») админка всё равно нужна своя, и SQL-запрос по таблицам pg-boss пишется проще, чем интеграция чужого UI.

**Условия обратного переезда на BullMQ** (фиксирую заранее, чтобы решение было проверяемым): устойчиво больше 100 задач в секунду; либо появился распределённый rate limiter с точностью до миллисекунд между несколькими инстансами; либо очередь начала заметно конкурировать с бизнес-нагрузкой за ресурсы БД. Абстракция `Queue` в коде делает замену локальной.

**Про Redis отдельно.** Он не нужен для очереди, но пригодится, когда API станет многоинстансным, — под кэш мапингов amoCRM и общий rate limiter. Пока инстанс один, token bucket живёт в таблице под `FOR UPDATE`: при десятках сообщений в день это точнее и проще, чем распределённый лимитер. Добавление Redis позже — изолированное изменение.

## ADR-005. Мессенджер-шлюз вместо своих провайдеров

**Заменяю.** Полное обоснование — в [02-critical.md](02-critical.md), R1. Коротко: Telegram Bot API не может писать первым, свой MTProto-клиент нарушает ToS и переносит на нас бан-риск и поддержку, а готовый шлюз с нативной интеграцией в amoCRM умеет писать первым по номеру и по username и сразу кладёт переписку в карточку сделки. Экономия — порядка 60–80 часов разработки и весь класс задач по поддержке транспорта. Интерфейс `MessagingProvider` сохраняем, чтобы транспорт можно было заменить.

## ADR-006. Наблюдаемость по размеру проекта

**Убираю Loki, сдвигаю Prometheus и Grafana.** Полный стек наблюдаемости на один VPS — это больше движущихся частей, чем само приложение, и требование п. 19 ТЗ он не закрывает: «понятно, где сломалось» здесь означает бизнес-цепочку событий по конкретному контакту, а не графики CPU.

На MVP: Sentry для ошибок, pino в JSON с маскированием ПД, таблица `automation_events` с correlation_id как основной инструмент разбора, `/health` и `/metrics` (prom-client — десяток строк, отдаём сразу, чтобы потом было что собирать), внешний uptime-мониторинг. Grafana и Prometheus поднимаем на релизе 3+, когда появится реальный трафик и второй сервер. Loki — только если серверов станет больше одного.

## ADR-007. Metabase на релиз 4

**Сдвигаю.** Metabase — правильный выбор для BI, и своё BI писать не надо, здесь план верен. Но на MVP данных для дашбордов ещё нет, а Metabase — это JVM и порядка 2 ГБ RAM в постоянной аренде. До релиза 4 метрики п. 17 отдаём SQL-вьюхами и одной страницей в админке (она нужна менеджерам всё равно). Аналитические вьюхи проектируем сразу так, чтобы Metabase просто подключился к готовым `analytics_*` вьюхам, — тогда его появление не потребует переделок.

## ADR-008. Refine для админки

**Добавляю.** По ТЗ и плану админка — это десять страниц, из которых импорты, контакты, сделки, очередь сообщений, шаблоны, менеджеры и логи — типовой CRUD с фильтрами, пагинацией, сортировкой и формами. Писать это руками на TanStack Query — примерно две-три недели, которые лучше потратить на дедуп, лимиты и стейт-машину. Refine даёт data provider поверх REST, готовые таблицы и формы и при этом не забирает контроль над разметкой: под капотом остаются те же TanStack Query, React Hook Form и Zod из плана. Кастомные экраны (цепочка событий, разбор дублей) пишем как обычные React-страницы.

Авторизация — httpOnly cookie-сессии, не JWT в localStorage: админка работает с базой персональных данных, XSS-угон токена здесь стоит слишком дорого.

## ADR-009. Потоковый парсинг файлов

`csv-parse` в streaming-режиме и `exceljs` со streaming-reader. Пакет `xlsx` (SheetJS) из npm-реестра не использую: опубликованная в npm версия давно не обновляется и имеет известные уязвимости в парсере. Файл читается потоком, а не целиком в память, — иначе XLSX на 50 тысяч строк роняет воркер по OOM. Плюс жёсткие лимиты: размер файла, число строк, проверка реального типа содержимого.

## ADR-010. Тесты

Vitest вместо Jest (быстрее, единый конфиг с Vite на фронтенде). Testcontainers с PostgreSQL — обязательно: дедупликация, advisory locks, partial unique indexes и `SKIP LOCKED` на моках не проверяются в принципе, а это самая ответственная часть системы. amoCRM подменяем stub-сервером на основе её OpenAPI-описания. Десять e2e-сценариев из плана оставляю без изменений, они покрывают ровно правильные вещи.

## ADR-011. Инфраструктура

Один VPS, Docker Compose: `postgres`, `api`, `worker`, `web`, `caddy`. Caddy вместо Nginx — автоматические сертификаты и короткий конфиг. GitHub Actions: линт, типы, тесты, сборка образов в registry, деплой по SSH. Kubernetes не нужен и не будет нужен на этих объёмах.

Бэкапы: ежедневный `pg_dump` плюс WAL-архивация в объектное хранилище, и — обязательно — регламентная проверка восстановления. Бэкап, который никто не восстанавливал, бэкапом не является. Секреты в переменных окружения, OAuth-токены amoCRM в БД в шифрованном виде.
