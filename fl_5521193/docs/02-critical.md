# 2. Критические моменты и решения

Восемь рисков, способных обрушить проект. Для каждого — суть, почему это критично и что конкретно делаем.

---

## R1. Первое касание в Telegram технически невозможно ботом

**Суть.** Telegram Bot API устроен так, что бот может отправить сообщение только в чат, который пользователь открыл сам (нажал Start, написал боту, перешёл по deep link). Наличие `@username` или Telegram ID не даёт права на первое сообщение. Это не антиспам-эвристика, которую можно обойти, а свойство платформы. Заказчик в п. 20 ТЗ обозначил риск верно.

**Почему критично.** Пункты 7, 8, 9, 11 ТЗ — то есть половина бизнес-ценности — опираются на исходящее первое сообщение. Если не решить до старта, релиз 3 нечего будет реализовывать.

**Варианты и оценка.**

| Вариант | Работает? | Риск | Вердикт |
| --- | --- | --- | --- |
| Telegram Bot API | Нет | — | Отпадает по определению |
| Свой MTProto-клиент (userbot на аккаунте менеджера) | Да | Нарушение ToS Telegram, бан номеров, вся ответственность и поддержка на нас, ~2–3 недели разработки | Не рекомендую |
| **Мессенджер-шлюз с нативной интеграцией в amoCRM (Wazzup24, Radist.Online)** | **Да, включая инициацию по `@username`** | Плата за канал, лимиты диалогов по тарифу, риск бана номера остаётся | **Рекомендую** |
| WhatsApp Cloud API (официальный) | Да, но шаблонами и с opt-in | Cold outreach нарушает политику Meta, блокировка номера | Только как второй канал по согласию |
| Email | Да | Домен в спам-листы, низкий отклик | Как дополнительный канал, с отдельным домена и прогревом |
| Telegram Ads / контент → входящий трафик | Да | Не работает по конкретному списку | Хороший дополняющий канал, не заменяет аутрич |
| Ручная отправка менеджером, система готовит очередь и текст | Да | Ограничена людьми | Обязательный fallback для контактов без автоканала |

**Решение.** Мессенджер-шлюз плюс fallback на ручную отправку.

Что это даёт кроме собственно отправки: шлюз кладёт всю переписку в карточку сделки amoCRM (пункт 10 ТЗ выполняется без нашего кода), менеджер продолжает диалог в привычном интерфейсе, а наш backend интегрируется ровно с одной внешней системой — amoCRM. Мы не пишем ни Telegram-, ни WhatsApp-провайдер.

Что важно учесть при закупке: у Wazzup тариф INBOX не позволяет писать первым, нужен минимум PRO; тарифицируется каждый канал (номер) отдельно, лимит диалогов обнуляется первого числа месяца. Это прямо влияет на пропускную способность системы, поэтому число каналов — вход в расчёт темпа, а не деталь оплаты.

Риск бана номера остаётся при любом транспорте. Митигация встроена в систему: дозирование 10–30 контактов в день на канал (п. 7 ТЗ), джиттер 60–180 секунд между отправками, окно отправки по локальному времени контакта, прогрев новых номеров, ротация каналов, немедленная остановка канала при первом Flood-ответе, персонализированный текст-вопрос вместо шаблонного оффера.

Абстракция `MessagingProvider` из плана всё равно нужна — но её первой и единственной реализацией на MVP становится `AmoChatsProvider` поверх шлюза. Так замена транспорта не заденет бизнес-логику.

## R2. Правовая база: спарсенные персональные данные и реклама без согласия

**Суть.** Мы обрабатываем персональные данные, собранные из открытых источников без согласия субъекта, и отправляем на них коммерческое сообщение. Здесь два разных правовых сюжета: обработка ПД (152-ФЗ, уведомление РКН, ответственность по ст. 13.11 КоАП, с 2025 года — оборотные штрафы за утечки и ст. 272.1 УК за незаконный оборот ПД) и рассылка рекламы (ч. 1 ст. 18 ФЗ «О рекламе» требует предварительного согласия абонента на рекламу по сетям электросвязи; ответственность по ст. 14.3 КоАП, жалоба в ФАС инициируется одним получателем).

**Почему критично.** Это не техническая задача, и её нельзя закрыть кодом. Но если проектировать без неё, то через полгода правки придётся вносить в схему БД и в модель разрешений, а не в конфиг.

**Я не юрист, поэтому дальше — не юридическое заключение, а перечень технических крючков, которые я закладываю, чтобы позиция заказчика была защитимой, и один содержательный аргумент в её пользу.**

Аргумент такой: первое сообщение по п. 9 ТЗ сформулировано как вопрос о профессиональной практике, а не как предложение товара. Это B2B-коммуникация с указанием себя и цели, и она заметно ближе к деловому запросу, чем к рекламе. Полностью риск ст. 18 это не снимает — квалификацию даёт ФАС по содержанию, — но конструкция ТЗ здесь уже лучше типового «предлагаем стать партнёром», и её стоит сохранить именно в таком виде.

**Что реализую:**

1. Журнал происхождения каждого контакта: источник, URL, дата и способ получения, ID импортной строки. Обязательные поля, не опциональные. Без этого невозможно ответить ни на запрос субъекта, ни на запрос регулятора.
2. Suppression-list с приоритетом выше любой автоматизации: два уровня — пауза до даты и постоянный запрет по каналу или глобально. Проверка стоит в самом низком слое отправки, обойти её из бизнес-кода нельзя.
3. Отписка в один шаг в каждом сообщении и обработка «не пишите мне» как немедленного постоянного запрета.
4. Реализация прав субъекта: экспорт и удаление данных по контакту одной операцией, с сохранением факта запроса в аудите.
5. Поле правового основания у контакта и запрет автоматической отправки при основании «нет».
6. Маскирование ПД в логах, шифрование OAuth-токенов, отдельные роли доступа, аудит всех действий администраторов.
7. Хранение только тех полей, которые реально используются в воронке.

**Что должен сделать заказчик** (вне разработки): консультация юриста по обеим темам, уведомление РКН об обработке ПД, политика обработки ПД на сайте, договоры с обработчиками (хостинг, мессенджер-шлюз), решение о географии базы — при контактах из ЕС включается GDPR с существенно более жёстким режимом.

## R3. Дедупликация по amoCRM как источнику истины не работает

**Суть.** Пункт 3 ТЗ предписывает проверять дубли в amoCRM. Практически это упирается в три вещи: поиск amoCRM работает по подстроке и не нормализует телефоны (`+7 916 123-45-67` и `89161234567` — для него разные строки); на каждую проверку уходит запрос из бюджета 7 rps на интеграцию; между проверкой и созданием есть окно, в которое второй воркер создаст дубль.

**Почему критично.** Заказчик сам называет это «критически важным, иначе CRM быстро заполнится дублями». Наивная реализация именно так и заполнит.

**Решение.** Локальный реестр идентификаторов в PostgreSQL — источник истины для дедупа, amoCRM — рабочий интерфейс.

1. **Bootstrap.** Одноразовая выгрузка всех существующих контактов и сделок amoCRM в локальный реестр батчами по 250 с соблюдением rps. Ориентир: 20 тысяч контактов — около часа.
2. **Нормализация.** Отдельный модуль чистых функций: телефон в E.164, email в lowercase, username без `@` и без URL-обёртки, URL в каноническую форму. Каждое значение попадает в `contact_identifiers` с типом. Полное покрытие unit-тестами — этот модуль определяет качество всей дедупликации.
3. **Уникальность на уровне БД.** `UNIQUE (type, normalized_value)`. Не «проверили и вставили», а ограничение, которое физически не даст создать второй такой идентификатор при любой конкуренции.
4. **Блокировка.** `pg_advisory_xact_lock(hash)` по хешу ключевого идентификатора внутри транзакции: два воркера с одним и тем же телефоном выстраиваются в очередь, лок снимается сам при коммите или откате.
5. **Порядок поиска** из ТЗ: телефон → Telegram ID → email → username/URL.
6. **Нечёткие совпадения не мержим автоматически.** Совпадение по ФИО и городу без совпадения идентификаторов — это кандидат в таблицу `duplicate_reviews` и решение человека в админке. Автослияние необратимо портит данные.
7. **Синхронизация.** Вебхуки amoCRM на изменение контактов и сделок обновляют реестр; ночная reconciliation ловит расхождения, если вебхук потерялся.

## R4. Лимиты amoCRM API

**Суть.** Официальные ограничения: не более 7 запросов в секунду на одну интеграцию и до 50 на весь аккаунт. Превышение — HTTP 429, при многократном нарушении аккаунт блокируется и на любой запрос отдаёт 403.

**Почему критично.** Импорт «десятков тысяч контактов» без единого регулятора скорости гарантированно приводит либо к 429 в цикле, либо к блокировке всего аккаунта — то есть к остановке работы отдела продаж, а не только нашей интеграции. Отдельно опасно то, что бюджет 50 rps аккаунта делится со всеми прочими интеграциями клиента (телефония, аналитика), и мы про них ничего не знаем.

**Решение.**

- Единый throttled-клиент — единственная точка выхода в amoCRM. Никаких прямых вызовов из модулей. Целевая скорость с запасом: 5 rps, не 7.
- Все обращения к amoCRM — только через очередь, синхронных вызовов в HTTP-обработчиках нет.
- Батчевые эндпоинты: до 50 сущностей за запрос вместо запроса на сущность. Импорт 20 тысяч контактов превращается из 20 тысяч вызовов в 400.
- Exponential backoff с jitter на 429 и 5xx, отдельная обработка 401 (обновление токена и один повтор), отдельная — 403, при котором интеграция уходит в аварийный стоп с уведомлением, а не продолжает долбить API.
- Вебхуки вместо опроса.
- Расчёт пропускной способности до старта импорта и явное предупреждение в админке, если импорт займёт больше N часов.
- Если бюджета не хватает — платные пакеты расширения лимитов amoCRM. Это вопрос к заказчику, а не к коду.

## R5. Гонка «ответ пришёл в момент отправки»

**Суть.** Пункт 12 ТЗ: любой ответ останавливает автоматизацию. Между «джоба взяла сообщение в работу» и «сообщение ушло» проходит время, и ответ может прийти именно в этот момент. Отменить джобу в очереди недостаточно — она уже выполняется.

**Почему критично.** Это худший из возможных сбоев с точки зрения бизнеса: человек ответил «не интересно», а через минуту получил автоматический follow-up. Такое чинится не извинениями, а архитектурой.

**Решение.**

1. Статус автоматизации хранится отдельно от статуса сделки amoCRM. Это разные вещи с разными жизненными циклами.
2. Перед фактической отправкой воркер в одной транзакции берёт `SELECT ... FOR UPDATE` по сделке, перечитывает `automation_status` и `last_reply_at` и только потом отправляет. Решение принимается на свежих данных под блокировкой, а не на данных из payload джобы.
3. У каждого исходящего сообщения — `idempotency_key` с уникальным индексом (сделка + шаг сценария). Повтор джобы после сбоя сети не даёт второго сообщения.
4. Входящее сообщение атомарно: `automation_status = STOPPED_BY_REPLY`, этап сделки → «Ответил», задача менеджеру. Одной транзакцией.
5. Дополнительно отменяем запланированные джобы — но как оптимизацию, а не как гарантию.
6. e2e-тест ровно на этот сценарий: ответ приходит между захватом джобы и отправкой; ожидание — второе сообщение не ушло.

## R6. Атрибуция продаж отсутствует в ТЗ

**Суть.** Пункт 17 требует показывать «количество лидов от каждого партнёра» и «продажи от каждого партнёра», пункт 16 — этапы «первый клиент» и «первая продажа». Но ТЗ нигде не говорит, откуда система узнаёт о продаже и как связывает покупателя с партнёром.

**Почему критично.** Это конечная метрика всего проекта: смысл привлечения партнёров — продажи, а не регистрации. Заказчик сам пишет об этом в п. 18. Без источника данных релиз 5 не проектируется.

**Решение** (требует подтверждения заказчиком):

- У каждого подключённого партнёра — уникальный промокод и реферальная ссылка с UTM. Это даёт атрибуцию на стороне магазина без интеграции по персональным данным клиента.
- Источник событий о продажах: вебхук магазина или платёжной системы, либо ночная синхронизация, если вебхуков нет.
- Локальные таблицы `partners`, `referrals`, `orders`; атрибуция по промокоду, затем по реф-ссылке, затем ручная привязка менеджером.
- Наверх, в amoCRM и в аналитику, отдаём агрегаты по партнёру.

Нужно знать: где именно происходят продажи (свой сайт, маркетплейс, офлайн), есть ли API или вебхуки, кто заводит промокоды.

## R7. Дозирование, лимиты и окна отправки

**Суть.** Пункт 7 ТЗ: 10–30 новых контактов в день на менеджера или аккаунт. Это ограничение против бана и жалоб.

**Решение.** Token bucket на два измерения — канал (номер) и менеджер, — с дневным лимитом из конфига. Окно отправки по локальному времени контакта (по умолчанию 10:00–19:00 в рабочие дни). Джиттер 60–180 секунд между сообщениями одного канала: ровный интервал сам по себе выглядит как бот. Отдельный глобальный предохранитель на весь проект.

Принципиальная деталь: при исчерпании лимита сообщение **переносится на следующее окно, а не падает с ошибкой**. Ошибка здесь означала бы потерянный контакт и ложную статистику доставки.

## R8. Наблюдаемость: «должно быть понятно, где именно сломалось»

**Суть.** Требование п. 19 ТЗ.

**Решение.** `correlation_id` присваивается импортной строке и проходит через всю цепочку: строка → контакт → сделка → назначение → сообщение → доставка → ответ → задача. Все значимые события пишутся в `automation_events` с этим ID. Страница «Логи интеграции» в админке показывает цепочку по контакту одним запросом, включая фактический текст отправленного сообщения (не ID шаблона — шаблоны меняются, а спорить с получателем придётся о конкретном тексте). Ошибки в Sentry, логи в JSON с маскированием ПД.
