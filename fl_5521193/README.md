## Короткое резюме

**Основной вывод по ТЗ.** Бизнес-логика описана хорошо и реализуема. Три пункта ставят под угрозу весь проект, если не решить их **до** начала разработки, и все три — не про код:

1. **Канал первого касания.** Telegram Bot API не может написать пользователю первым — это архитектурное ограничение платформы, а не задача, которую можно «доделать». Нужен другой транспорт (см. решение ниже).
2. **Правовая база.** Спарсенная база — это персональные данные без согласия субъекта. Рассылка коммерческого предложения по такой базе попадает под ч. 1 ст. 18 ФЗ «О рекламе» (реклама по сетям электросвязи только с предварительного согласия) и под 152-ФЗ. Технические крючки под комплаенс закладываю сразу, но решение о запуске — за заказчиком и его юристом.
3. **Источник данных о продажах.** ТЗ требует аналитику «продажи от каждого партнёра», но не указывает, откуда система узнаёт о продаже. Без ответа последний релиз спроектировать нельзя.

**Ключевое решение по архитектуре.** Не писать свои интеграции с Telegram и WhatsApp. Использовать готовый мессенджер-шлюз, нативно встроенный в amoCRM (Wazzup24 или Radist.Online): он умеет инициировать диалог в Telegram по номеру и по `@username`, кладёт переписку прямо в карточку сделки и отдаёт входящие через amoCRM. Наш backend тогда общается ровно с одной внешней системой — amoCRM API + вебхуки. Это снимает с проекта самый рискованный и самый трудоёмкий кусок. Детали, риски и цена — в [docs/02-critical.md](docs/02-critical.md).

**Основные правки к предложенному стеку** (полностью — в [docs/04-stack-adr.md](docs/04-stack-adr.md)):

- Модульный монолит — согласен, оставляю. Два деплой-юнита из одного репозитория: `api` и `worker`.
- NestJS — оставляю (на Fastify-адаптере). Модули, DI, guards и генерация OpenAPI здесь окупаются.
- **Redis + BullMQ убираю из MVP, беру pg-boss** (очередь на PostgreSQL). Главная причина не в экономии контейнера: задачу можно поставить в той же транзакции, что и бизнес-запись, поэтому расхождение «контакт создан, а джоба потерялась» становится невозможным без отдельного outbox. Нагрузка проекта на два порядка ниже потолка pg-boss, а сверху всё равно стоит жёсткий лимит amoCRM в 7 запросов в секунду. Условия обратного переезда на BullMQ прописаны в ADR-004.
- **Prisma меняю на Drizzle.** Проекту нужны advisory locks, partial unique indexes, `INSERT ... ON CONFLICT`, `FOR UPDATE SKIP LOCKED` и materialized views — то есть ровно те места, где Prisma выталкивает в нетипизированный `$queryRaw` и где как раз живут гарантии от дублей.
- **Prometheus + Grafana + Loki убираю из MVP.** Sentry, структурированные JSON-логи (pino) и таблица `integration_logs` под страницу «Логи интеграции», которая по ТЗ нужна всё равно. Метрики отдаём эндпоинтом сразу, стек визуализации поднимаем, когда появится второй сервер.
- **Metabase сдвигаю на релиз 4.** Пункт 17 ТЗ на MVP закрывается SQL-вьюхами и одной страницей дашборда в админке. Metabase — это JVM и ~2 ГБ RAM, платить за них до появления данных смысла нет.
- **Админку строю на Refine + shadcn/ui**, а не с нуля. Из десяти страниц ТЗ восемь — типовой CRUD с фильтрами и пагинацией; готовый каркас экономит порядка двух-трёх недель без потери контроля над кодом.
- Парсинг файлов — потоковый: `csv-parse` и `exceljs` в streaming-режиме. Пакет `xlsx` (SheetJS) в npm не беру.

**Что добавляю к ТЗ по своей инициативе,** потому что без этого система развалится на проде: suppression-list с приоритетом выше любой автоматизации, журнал источника каждого персонального данного, token bucket на канал и на менеджера с окном отправки, идемпотентность на уникальных ключах вместо надежды на «не выполнится дважды», очередь ручной обработки для контактов, до которых нельзя дотянуться автоматически, и ночная reconciliation с amoCRM.
